## 本轮已实现

### H1：业务 Mock 响应保真

- 问题：管理 API 和业务响应共用 `sendJson`，错误状态下会给对象添加 `code`，也会把数组展开成对象。
- 修复：拆分 `sendMockJson` 与管理/诊断响应封装；独立 Mock、旧接口直连和旧接口经统一分发均原样序列化响应体。管理 API、鉴权失败和组合顺序错误继续返回稳定错误码。
- 验证：`server/response-fidelity.test.mjs` 覆盖成功及错误状态、对象、数组、空值、字符串、布尔、数字，以及空/已有 `code`；同时检查状态码和命中响应头。

### H2：Whistle CLI 异步同步

- 问题：`spawnSync` 在 CLI 等待期间阻塞同进程的 Mock 和管理 API。
- 修复：使用异步 `execFile`，保留 8 秒执行超时，超时强制终止 CLI，并限制输出为 1MB。继续通过既有串行队列同步最新配置，保留同步结果持久化与 Whistle 回读验证。
- 行为：发起配置变更的请求仍等待同步结果；其他管理读取和 Mock 请求可在同步等待期间正常处理。保存成功与同步失败仍分别表达。
- 验证：`server/whistle-sync.test.mjs` 用文件握手阻塞隔离 CLI，确认释放前管理读取及 Mock 已完成，并检查失败记录和后续重试。
- 后续第二轮已补充规则摘要去重、同步请求合并与定时回读，见下方 P1 进展。

以下保留各项设计与验收依据。


### P1-1：减少重复同步，并准确展示代理健康状态

入口：`server/whistle.mjs`、`server/index.mjs`、`server/v2-api.mjs`、`app/page.tsx`。

方案：

1. 对编译后的有效规则生成摘要，仅在代理匹配范围改变时自动提交；响应正文、名称、计数和组合进度变化无需提交相同规则。
2. 记录期望规则版本、最后验证成功版本和同步错误。失败不更新成功摘要，相同配置后续仍应重试。
3. 合并等待队列内的连续配置变更，每轮读取最新注册表。并发调用者等待覆盖其变更版本的同步结果，不能把旧版本成功当作新版本成功。
4. 手动同步和启动同步强制提交，不能被摘要缓存跳过；代理重启或托管规则被外部修改后也需重新校验。
5. 分开展示“上次同步成功”“当前连接可用”“规则已验证”，定期健康检查并在重连后恢复最新规则。
6. 为客户端配置读取和规则回读设置完整截止时间，避免只依赖 socket 空闲超时。

验收：连续编辑最终只应用最新规则；失败后重试正常；清空规则仍覆盖旧配置；Whistle 重启、规则被手动改写后可恢复；显示状态不把历史成功当作当前在线。

### P1-2：响应头校验与发送结果记录

入口：`server/model.mjs`、`server/rules.mjs`、`server/dispatcher.mjs`、`server/index.mjs`。

方案：保存前统一使用 Node `validateHeaderName` / `validateHeaderValue` 校验，覆盖新旧模型及导入。业务自定义头与内部保护头按不区分大小写处理。明确非 Latin-1 值需要调用方编码，不能静默修改语义。运行日志区分 selected、finished、failed、aborted；`finish` 只表示服务端交付响应数据，不表示浏览器已成功读取。

保留请求匹配时推进组合的并发语义，不因客户端断开直接回滚共享状态；另行展示发送结果和匹配次数，避免把它们称为客户端成功次数。

验收：中文值、控制字符和无效头名在保存阶段返回稳定的 400 错误且不落盘；合法头可正常发送；客户端断开和发送失败可诊断；并发组合进度仍不重复。

### P1-3：形成完整的浏览器跨域策略

入口：规则编译、分发器、响应封装、Mock 编辑器。

方案：区分“手动配置”和“允许指定页面来源”的跨域模式。自动模式依据 Origin 白名单处理 OPTIONS、请求方法、请求头和 credentials，设置适当的 `Vary`。预检不计业务命中、不推进组合；显式 OPTIONS Mock 与自动预检的优先级必须明确。组合 409 和分发诊断也应用同一跨域策略。管理 API 的来源与令牌策略独立保留。

验收：真实浏览器覆盖 JSON POST、自定义认证头、带凭据请求、预检被拒绝、组合 409；确认预检未进入真实接口且未推进业务进度。HTTP 客户端收到响应不能替代浏览器验收。

### P1-4：项目切换草稿保护与过期编辑冲突

入口：`app/page.tsx`、`components/mock-workspace.tsx`、配置变更 API。

方案：草稿状态或 dirty 检查提升到页面层，项目切换统一检查未保存输入；可以按项目缓存草稿。将配置 revision 与运行状态分离，编辑器打开时保存 revision，提交时携带预期版本；版本过期返回 409，并保留草稿供对照。轮询到新版本不能自动更新草稿所绑定的旧 revision。

验收：切换项目、关闭侧栏、刷新页面均有保护；两个窗口交叉编辑不会静默覆盖；纯命中计数变化不会制造配置冲突；保存中切换项目不会串写数据。

## 待实现：性能与运行保障

### P2-1：配置、运行进度与命中日志分离

问题：每个分发请求都走完整注册表读写，包括未命中回源；快照和正文越多，请求成本越高。

方案：先建立响应体积、规则数量、并发数的基准，记录吞吐、延迟和写入量。采用经过校验的内存配置快照，配置修改时原子替换；进度与命中日志独立存储。未命中只读配置，不重写文件。如引入 SQLite，进度选择与推进仍需在同一事务完成，并明确进程崩溃后的恢复语义；不能简单通过日志延迟落盘牺牲步骤唯一性。部署明确单写进程或增加跨进程锁。

验收：未命中不产生配置写入；大正文不随每次命中重复写入；并发无重复步骤；磁盘写入失败不会静默推进；重启恢复结果符合约定。以基准前后对比决定是否继续复杂化。

### P2-2：管理页面轻量刷新

方案：拆分配置摘要、按需读取的响应正文、运行状态和命中增量接口。先采用 revision/ETag 与增量游标，再按实际需要增加 SSE。暂停隐藏页面轮询，取消旧项目未完成请求，避免旧响应覆盖新项目记录。

验收：轮询不携带全部响应正文及恢复快照；切换项目无串数据；后台页面减少请求；断线恢复和命中日志截断能正确处理。

### P2-3：回源语义与退出恢复

问题：Node 直接回源绕过 Whistle 请求链路，不保证沿用其 host、上游代理、客户端证书等配置。源码模式退出后规则可能残留；重启后运行凭据变化，旧规则在同步恢复前可能返回 403。

方案：定义并文档化直连回源的边界，增加 Whistle 适配层；评估原生插件透传或受控回流代理，必须防止再次进入分发器。统一处理 SIGINT/SIGTERM 的有限时清理，桌面进程等待子服务完成清理后退出。异常退出无法保证清理，应在启动时检测残留并重新验证规则。不要通过接受任意旧凭据来解决残留问题。

验收：覆盖 host 映射、上游代理、TLS 客户端证书、慢流与客户端断开；正常退出清除规则；代理离线时退出有上限；异常退出重启可恢复，且内部凭据不泄漏。

### P2-4：URL 日志脱敏与本地访问边界

方案：对 `actualUrl`、顺序错误实际地址和配置地址中的敏感查询参数采用一致脱敏策略，匹配仍使用原始 URL。检查日志、API、导出和备份的边界。逐步收敛旧 `/runtime/respond/:id` 直连入口，增加鉴权或默认关闭；提供兼容迁移说明。管理配置、令牌及生成文件设置合理本地权限。

验收：URL 中的 token、手机号等不会出现在命中日志和诊断错误中；脱敏不改变匹配；旧接口不能被无授权调用推进共享流程；现有受信代理回归通过。

## 待实现：产品能力与工程简化

### P3-1：匹配解释器

输入 URL 和方法，在配置与运行状态的只读快照中执行匹配分析。返回候选、优先级、被遮挡规则、当前等待步骤及不匹配原因。抽取与真实分发共用的纯匹配逻辑，不能通过调用有副作用的分发器模拟。

验收：解释结果与下一次同状态的真实请求一致；不推进组合、不增加计数、不写日志、不触发回源。

### P3-2：结构化匹配与可选会话进度

方案：逐步增加 host/path、指定 query 和 JSON 字段匹配，明确缺失字段、类型和编码语义；限制请求体大小、解析时间，非法 JSON 不破坏转发。扩展 Whistle 候选范围与跨项目冲突判断，不能仅修改最终匹配器。项目全局进度继续作为默认模式，多人使用时再提供按显式会话标识隔离的模式，设置过期和重置机制，不以 IP 隐式识别用户。

验收：同 URL 不同业务字段可区分；候选规则不漏请求；冲突提示可解释；会话间互不推进，同一会话并发仍保持唯一步骤。

### P3-3：构建与 Whistle 接入简化

方案：评估统一 React + Vite 的 Web/桌面构建，移除不需要的 RSC/Cloudflare 链路。集中管理端口、数据目录和 Whistle 路径配置。增加 Whistle 版本/能力探测，官方 API 或原生插件作为适配器实现，保留独立领域模型、CLI 与编辑器。桌面发布另行完成签名、公证、安装升级和新设备验证。

验收：源码启动与桌面构建复用页面；自定义端口前后端一致；Whistle 不存在/版本不兼容时提示明确；升级保留用户数据；插件适配不改变 Mock 和组合语义。

## 后续实施顺序

1. P2-1、P2-2：先建立基准，再分离配置/运行数据及轻量刷新。
2. P2-3、P2-4：代理生命周期、回源和本地数据边界。
3. P3：匹配诊断、结构化匹配、会话及构建简化。

P1 已完成，不再列为下一轮待办。CLI 等未提供 If-Match 的旧调用保持兼容；需要防止过期覆盖的客户端，应读取 `/api/state` 的项目 `revision`，并在修改项目内资源时提交带双引号的 `If-Match`。版本涵盖配置与项目总开关，不涵盖命中、进度和发送结果。

健康检查通过 `/api/whistle/check`（POST）回读并在需要时恢复规则，`/api/whistle/sync`（POST）始终强制同步。自动去重只复用验证成功的规则，失败后不会跳过重试。周期检查不表示代理请求一定经过 Whistle；代理设置与证书仍需实际请求验证。

跨域设置保存在项目 `cors`：`{ mode: "allow-list", origins: ["https://page.example.com"], headers: ["content-type", "authorization"], credentials: true }`。显式 `manual` 模式仅使用响应配置中的跨域头；未配置策略的旧项目维持原有通配行为。显式 OPTIONS Mock 优先于自动预检。

发送字段 `delivery` 为 `selected` / `finished` / `failed` / `aborted`，其中 `finished` 只代表服务端已发送，不保证浏览器业务代码成功读取。失败或断开不回滚共享组合步骤。发送结果目前独立追加一次注册表事务，这部分写入成本将在 P2-1 中与运行存储一起优化。

每项实施时补充对应边界回归，并更新本文状态。避免将当前全部待办一次性引入，尤其不要在缺少基准和恢复约定时直接改写存储层。
